先看结论

最重要的判断：XB-SVCB 的桌面进程是一个 pywebview GUI 宿主；主进程启动时完成路径探测、数据目录准备、服务对象装配和前端加载，但不会把所有模型权重一次性加载进主进程。模型推理发生在任务真正运行时，由对应的隔离 Python 环境启动 Worker 子进程。

主进程

run.ps1 / run.bat → app/main.py → pywebview。前端通过 JS Bridge 调用 Api，应用服务和仓储都在这个 GUI 进程内。

模型进程

So-VITS-SVC、RVC、SeedVC、DDSP-SVC、UVR、AI 增强各自有隔离环境。一次性任务多数使用 subprocess.run；系统音频实时模式使用保持模型常驻的 JSON 行协议 Worker。

API 进程

FastAPI 默认关闭。用户在界面手动启动后，Uvicorn 在 GUI 进程的 xb-fastapi 后台线程运行，不额外创建 API 命令行进程。

共享队列

界面任务和外部 API 任务共用 ConversionService 的串行推理队列，共享模型库、作品库、临时目录和当前设备能力。

1. 桌面启动链路

安装版和源码运行的核心入口相同，区别主要在 Python 解释器路径和前端资源位置。

run.ps1 / run.bat检查 app/.venv
→
app/main.py单实例 + 解析前端 URL
→
config.py确定根目录、环境、数据目录
→
build_api()准备目录并装配服务
→
webview.create_window注入 JS API
→
webview.start加载生产构建或 Vite
阶段行为源码证据
启动命令run.ps1前台执行 app\.venv\Scripts\python.exe app\main.py；run.bat优先用 pythonw.exe 后台启动。run.ps1、run.bat
开发/生产--dev 或 XB_DEV=1 使用默认 http://localhost:5173；生产模式要求 web/dist/index.html 存在，并由 pywebview 内置 HTTP server 提供静态资源。app/main.py：is_dev、resolve_url
单实例已有实例时通知原窗口置前，新进程退出。app/main.py、single_instance.py
退出先关闭实时服务和 FastAPI，再清理当前数据目录的 temp 内容，最后释放单实例句柄。app/main.py、bridge.py
启动不等于模型加载：主进程只创建 SvcEngine、RvcEngine 等引擎包装器并注册路由；引擎的 available 是环境/脚本/仓库探测，真正的 checkpoint 加载在对应 Worker 内发生。

→
仓储models / works / settings / editor
→
应用服务任务、模型、编辑器、实时、插件
→
ApiJS Bridge + HTTP facade
build_api()
  paths.ensure_dirs()
  ffmpeg, uvr = FfmpegTool(), UvrTool()
  svc, rvc, seedvc, ddsp = SvcEngine(), RvcEngine(), SeedVcEngine(), DdspSvcEngine()
  engines = EngineRegistry([svc, rvc, seedvc, ddsp])

  services = System / Model / Conversion / Work / Music / Hub / Editor / Plugin / Realtime
  work_service.recover_stale()

3. 普通单模型推理链路

单模型任务由 WorkService.create 建立作品记录并调用 ConversionService.start；转换服务在后台线程中串行处理队列。下面是实际主流程。

1. 输入标准化FFmpeg 解码为 WAV
→
2. UVR人声 / 伴奏分离
→
3. 人声修复DeepFilterNet3 / 分析
→
4. F0So-VITS 专属探针
→
5. 模型推理EngineRegistry 路由
→
6. 输出修复自然度保护 / 增强
→
7. 混音人声 + 伴奏 + FFmpeg
  1. 创建任务：选择默认模型或指定 model_id，解析模型文件角色，写入 works.json，状态为 queue。
  2. 输入：先用 FFmpeg 按内容解码并统一格式，避免扩展名与真实编码不一致导致 UVR 失败。
  3. 分离：UVR 调用 .venv-uvr 的 uvr_worker.py。可选使用 UVR-DeEcho-DeReverb.pth 对人声再去混响。环境未就绪时，auto 模式会降级为“源音频作为人声、无伴奏”；显式选择加速器时则严格报错。
  4. 修复/分析：可调用独立 .venv-vocal 的增强 Worker，对分离人声做 DeepFilterNet3 修复并分析高频/音域，调整高音域参数。
  5. F0：只有 So-VITS-SVC 走 f0_worker.py；RVC、SeedVC、DDSP-SVC 在各自推理内部处理或使用自身参数。
  6. 路由：framework 经过 EngineRegistry.for_framework 选择引擎；未知框架回退到默认 So-VITS-SVC。
  7. 收尾：模型输出再次做可选人声修复/增强，最后按策略混合人声与伴奏，输出保存到 data/works/<work_id>，完整子进程命令和 stdout/stderr 追加到 run.log。

主流程证据：work_service.py 的创建逻辑；conversion_service.py 的 _run_locked。

队列语义：作品页和 API 创建的任务进入同一个串行转换队列；“任务卡住”首先检查队列前序任务、作品目录的 run.log 和当前 Worker 子进程，而不是只看前端进度。

一次性 Worker 的共同协议

父进程（app GUI）
  subprocess.run([隔离环境 Python, worker.py, ...], cwd=上游仓库)
        │
        ├─ stdin：通常无请求，参数通过命令行传入
        ├─ stdout/stderr：父进程捕获并写入 works/<id>/run.log
        └─ output.wav：Worker 直接写出，父进程检查退出码和文件存在性

实时 Worker 的共同协议

PersistentInferenceSession
  Popen(..., stdin=PIPE, stdout=PIPE, stderr=STDOUT)
  等待 READY
  每个音频块写入一行 JSON：{"input": ..., "output": ..., ...}
  等待 RESULT\t<JSON>
  close 时写入 {"command":"close"}

核心实现：persistent_worker.py；配置探测：config.py。

5. 实时翻唱与系统音频链路

实时模式和普通整曲任务最大的差别是模型不能每个块都重新启动，否则启动和加载模型的成本会压垮实时性。因此系统音频模式使用常驻 UVR 与常驻 RVC/SeedVC Worker。

文件或 WASAPI/VB-CABLE输入混合音频
→
预缓冲 / 固定块保留上下文重叠
→
常驻 UVR只提取人声
→
常驻 RVC / SeedVC按块转换
→
等功率交叉淡化保留伴奏和时钟
→
播放 / 作品归档
  • 系统音频模式只允许单模型；文件模式支持实时分块播放并可登记为作品。
  • 相邻块带重叠上下文，输出端做等功率交叉淡化，减少卡顿、接缝和爆音。
  • UVR server 的标记是 UVR_SERVER_READY / UVR_SERVER_RESULT；推理 Worker 的具体 READY/RESULT 标记以各引擎实现为准。
  • 退出或停止会关闭会话；临时会话位于 data/temp/realtime-covers，完成后复制到作品目录。

服务入口：realtime_cover_service.py；UVR 常驻入口：uvr_tool.py。

安装器把“主程序环境”和“重型 AI 环境”拆开。完整安装通常由 install.ps1 触发；无 PowerShell 时可用 setup_env.bat。

install.ps1前置检查 / 参数

→

→

→
仓库 / 底模 / 模型下载或复制并校验
步骤创建/准备内容失败时优先重试

设备栈选择

安装器支持自动判断，或显式指定 --cpu、--directml、--gpu。NVIDIA 会选择 CUDA（当前脚本区分 cu121/cu128），Windows AMD 使用 DirectML，其余使用 CPU。显式要求加速器时，运行时会校验实际后端，不能用时应报错而不是静默冒充 GPU。

易混淆点：setup_env.bat 的注释说明它默认使用 --skip-app --skip-web，主要搭建重型 AI 环境和模型；如果 run.ps1 报 app/.venv 不存在，需要先做完整安装或单独执行 --only app。

10. 排错优先级

现象第一检查点处理方向
双击无反应 / 启动提示 runtime not foundapp/.venv/Scripts/python.exe完整安装，或 install.py --only app。
提示找不到前端构建产物web/dist/index.html在 web 执行 npm ci 和 npm run build，开发时用 --dev。
模型页显示未安装 / 降级模式应用状态页 + config.py 的环境路径探测检查对应 venv、worker、上游仓库 marker、模型文件；单独重跑环境安装。
任务卡在分离works/<id>/run.log、uvr.log确认 .venv-uvr、模型文件、FFmpeg；显式 DirectML/CUDA 时看实际 provider。
任务卡在模型推理run.log 中的完整命令、Worker stdout/stderr用日志里的 Python + worker 命令复现；核对主模型、配置、index/参考音频和设备。
CUDA 显存不足Worker 日志中的 OOM关闭占用显卡的程序，降低 DDSP 步数，缩短输入/切片，或改 CPU。
AMD DirectML 结果异常安装时 Python 版本、torch-directml、驱动、实际 backend优先 So-VITS/RVC；SeedVC 主要用于兼容/排障，检查 DirectML 专用补丁日志。
API 启动失败API 页面显示的端口错误、端口占用、scope确认 1024-65535、端口未占用；局域网模式检查 Windows 防火墙。
实时模式断续/延迟大UVR/模型常驻 Worker READY 是否及时出现看预缓冲、设备、块长、显存；不要把普通一次性推理命令当实时 Worker 使用。
重启后模型/作品消失data_home.json、XB_DATA_DIR确认实际数据目录，以及 models.json/works.json 是否可读。

推荐排查顺序

1 主程序能否启动 → 2 数据目录是否正确 → 3 环境状态是否 ready → 4 模型文件是否完整 → 5 Worker 命令能否单独运行 → 6 再看前端任务状态。

inference_device.pyauto/CUDA/ROCm/DirectML/CPU 解析、能力探针和兼容补丁。
http_server.pyFastAPI 路由、鉴权、Uvicorn 生命周期。
install/install.py环境创建、GPU stack 选择、仓库获取、底模部署与验证。
app/tests模型服务、设备探针、Worker 参数、API、实时和安装回归测试。

建议的后续工程化改进

  • 增加一个统一的 CLI doctor 命令，输出数据目录、每个 venv Python、仓库 marker、模型完整性、实际设备 provider。
  • 把各框架 Worker 的 READY/OK/ERR 标记整理成一个小协议文档或常量模块，降低实时链路排查成本。
  • 为每次作品记录保存结构化的 runtime snapshot：Python 路径、Torch 版本、实际 backend、模型文件 hash；现在主要依赖文本 run.log。
  • 在 CI 中增加“无真实模型的启动 smoke test”和“每个隔离环境命令构造测试”，同时保留已有的框架专项测试。
